# Razorpay Test Mode Demo & Integration Guide

## Overview

ReTryPay supports real **Razorpay Test Mode** telemetry and manual link creation while enforcing absolute boundary isolation, policy supremacy, and data hygiene.

> [!IMPORTANT]
> **Razorpay Test Mode telemetry is real integration data but is strictly separate from local simulation and synthetic evaluation.**
> Live keys (`rzp_live_`) and live payment execution are strictly banned in code and configuration.

---

## 1. Safety and Security Rules

1. **No Live Keys**: Configuration fails on startup if any key begins with `rzp_live_` or if `RAZORPAY_TEST_MODE_ONLY` is set to `false`.
2. **Customer Safety**: Real notifications are permanently disabled (`notify={"sms": false, "email": false}`). Customer communication is simulated and recorded to sanitized local audit logs only.
3. **No Automatic External Calls**: Standard webhook processing never makes automatic outbound HTTP calls to Razorpay. External link creation requires explicit manual CLI authorization.
4. **Header Non-Authority**: Request headers (e.g. `X-Event-Source`) cannot alter event source classification. Event source is 100% server-derived.

---

## 2. Server-Derived Event Sources

All ingested events, recovery cases, orders, and payment links are tagged with an explicit `EventSource`:

| EventSource | Ingestion Origin | Description |
| :--- | :--- | :--- |
| `RAZORPAY_TEST_MODE` | `EXTERNAL_RAZORPAY_WEBHOOK` | Received via `/api/v1/webhooks/razorpay` with valid Razorpay HMAC signature |
| `LOCAL_SIMULATION` | `INTERNAL_SIMULATOR` | Generated by `/api/v1/simulator/trigger` scenario runner |
| `SYNTHETIC_EVALUATION` | `OFFLINE_EVALUATOR` | Offline 1,000-case counterfactual evaluation dataset |
| `FAKE_PROVIDER` | `UNIT_TEST_HARNESS` | Test harness and mock provider execution |

---

## 3. Source-Partitioned Identifier Isolation

To prevent collision or cross-source merging between local simulation and real Razorpay Test Mode:
- Every table enforces composite uniqueness: `(source, order_id)`, `(source, payment_id)`, `(source, provider_event_id)`, and `(source, provider_link_id)`.
- A webhook for `order_123` in `RAZORPAY_TEST_MODE` will never match, overwrite, or close an `order_123` in `LOCAL_SIMULATION`.

---

## 4. Manual CLI Payment Link Workflow

To create a real Razorpay Test Mode Payment Link:

### Step 1: Configure Test Mode Environment
```bash
export RETRYPAY_ENV=demo
export RAZORPAY_PROVIDER_ENABLED=true
export RAZORPAY_KEY_ID=rzp_test_YourKeyId
export RAZORPAY_KEY_SECRET=YourSecret
export RAZORPAY_WEBHOOK_SECRET=YourWebhookSecret
```

### Step 2: Trigger or Ingest a Test Mode Failed Payment
Ingest a real test failure from the Razorpay Dashboard or via webhook tunnel. Note the resulting Case ID (e.g. `rcv_order_test_123456`).

### Step 3: Run the CLI Tool
```bash
python scripts/create_test_mode_payment_link.py --case-id <CASE_ID> --channel whatsapp
```

### Step 4: Follow the 5-Stage Safety Flow
1. **Preflight Validation**: Validates environment, keys, consent, budget, and deterministic policy eligibility.
2. **Display Summary**: Shows Case ID, masked Order ID, amount, and channel.
3. **Exact Confirmation**: Prompts user to type `CREATE TEST MODE PAYMENT LINK`.
4. **Transactional Execution**: Runs fresh policy re-check, reserves budget, calls Razorpay API, and commits reservation.
5. **Terminal Output**: Displays full Short URL (`https://rzp.io/i/...`) and link identifiers directly in the terminal.

---

## 5. Privacy & Data Masking

- **Normal DTOs & Dashboard**: Payment Link IDs and merchant reference IDs are masked (`plink_***1234`, `ref_***5678`).
- **Audit Logs**: Raw webhook bodies and short URLs are excluded from `SanitizedAuditEventDTO`.
- **Evaluation Isolation**: Operational databases (`retrypay.db`) and evaluation databases (`retrypay_eval.db`) remain strictly segregated.
